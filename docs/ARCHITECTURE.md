# 代码结构

项目按入口、应用模块、前端、算法包、配置与测试分层。`src/`模块保持现有名称，便于已有命令行和缓存流程兼容；本轮不把正在使用的算法改写为一套新框架。

源码运行环境由 `pyproject.toml`、`uv.lock` 与 `.python-version` 管理，安装在项目 `.venv` 中；CPU / CUDA 使用互斥的依赖选项。入口和工作进程使用同一解释器，Windows 启动器在显式本机覆盖之后优先选择 `.venv`。运行依赖的安装与视频、模型和结果目录分离，桌面发行包仍使用独立打包的运行时。

|职责|主要文件|

数据流：视频与人工输入 → SAM2跟踪 → 几何/时序姿态 → 个体身份与头尾 → 按质量条件生成指标 → 显示骨架与视频。正式测量与仅显示恢复保持分离。

单虫身体序列对短缺口尝试原分辨率中线恢复，由前后清晰帧的图像运动共同验证；原有候选和源帧排除不被覆盖。相邻帧对应必须通过几何或双向运动检查，断点切开头端确认与质心速度计算。冲突人工锚点保留并进入复核，不强迫连续虫体翻转。

`review_intervals.py` 从质量记录生成区间、清晰关键帧和前后参照，不授予测量权限。指标阶段保存 `review-intervals.json`，逐帧接口按同一规则生成复核计划；界面调用现有头端确认及派生任务流程，重算后重新生成待复核区间。恢复来源和前后锚点记录在逐帧数据，尝试失败原因保存在序列审计中。

单虫头尾在短断点两侧可由头端或尾端重新接回。`marked_end_recovery.py` 对两种端点对应分别作前向和反向运动检查，缺少完整中线的每一帧都需在轮廓上找到唯一相符的游离端点。原人工标记所在片段提供多帧外观参照，恢复后的片段不能成为新的外观模板。原标记、跨断点证据和端点可见性分别保存。此过程只定向已有中线，保留缺测帧和指标的质量门控。

`terminal_overlap.py` 增加固定舱室坐标下的局部重合检查。程序在端点附近找一段连续虫身，允许尖端沿这段虫身伸缩，并在每个缺口帧从可见端点沿掩膜骨架追到第一个分叉。只有同一段虫身在各帧都有唯一对应时，这项证据才能接回端点。两条分支重合时不给出重合判断，重合判断和端点运动冲突时停止接续。序列审计记录参与帧、对应区段、最大位置偏差和实际使用的证据。

连续画面在快速转弯时可能被拆成一至两个单帧片段。`short_turns.py` 比较两端在所有可能排序下的前后轨迹。只有一侧可追溯到人工标记时，轨迹与多帧外观共同支持的方向显示为 H?/T?。当两侧分别追溯到不同的人工标记时，程序从两端独立排序，对比中间每帧的实测端部与两处标记片段的外观。双向轨迹唯一且与两侧外观一致，才记录为跨断点恢复，并按原有质量条件计算指标。审计保存两侧参考帧、正反向排序的误差与外观比较结果。方向未定的 A/B 在导出视频中共用中性灰色。

无头尾标记的单虫视频中，程序也会检查夹在两个已定向片段之间的一至两帧。两端附近的实测虫身须分别符合前后位置变化，且两侧清晰帧提供的端部宽度和灰度特征须支持同一排序。结果以 H?/T? 显示，审计记录参考帧、两种对应的位置偏差及外观支持。人工确认与正式摆角仍使用原有条件。

连续多帧方向未定、两侧已定向帧之间相隔至多一秒时，程序从两侧分别追踪可见的端部。两端靠得很近时，还可用尖端附近虫身的朝向区分两种对应。每个原本连续的片段单独核对：至少一侧能接回运动轨迹，两侧清晰帧的外观均支持该排序，才给出候选头尾。两侧运动推断冲突、方向模糊或使用接触模型的帧继续保留未定。

若途中只有一处相邻帧的端点对应模糊，程序用断点附近四帧的实测端部比较两种运动轨迹，并从时间的两个方向核验排序。两侧原轨迹接回同一方向时，一张清晰参照帧可补充中位外观证据，但须与另一侧的模板在至少两个相同的目标帧上相互印证。相反的外观证据会阻止接续。审计记录轨迹比较和实际支持的帧号。

批处理状态快照在一次请求内复用任务摘要，任务配置仍保留独立深拷贝。`quality_audit.py` 按虫体一次分组，并在逐行统计时复用质量权限，保持原有计数、排除区间和证据语义。导出视频的解码器和编码器在成功、校验失败或取消时均释放。

单虫序列的拖影显示估计位于 `blurred_tips.py`。程序用虫体未占据该区域的帧估计静态背景，在两个对比度阈值下定位同一端部分出的两条影迹，并核对相邻帧的同端运动。头端取两影尖的中点。尾端比较两条影迹中段相对背景的暗度。两个阈值下的暗度差都超过局部噪声，且至少四张背景参照逐一剔除后仍选中同一影尖时，尾端标在该影尖上。深浅无法稳定区分时取中点。几何质量记录保存两处影尖、暗度、选点方法和参照帧。逐帧结果另存裁剪坐标系下的 `display_blur_{head,tail}_{x,y}_px` 和选点方法，视频用 ~ 标明显示估计。身体中线、头尾定向和表型测量各自使用原始证据。

身体序列的灰度帧与掩膜由 `body_frame_cache.py` 统一解码。两者合计不超过 256 MiB 时使用内存数组，更大时使用可由系统回收页面的磁盘映射；不降采样、不跳帧，也不将全序列求解改为独立分段。映射文件采用匿名或关闭即删除的临时文件，工作进程被终止时也由系统释放。当前方法直接使用求解器保存的头尾证据；旧基线的外观特征仅在对应兼容分支中提取。

Windows 选择 CUDA 时，单虫求解器在 GPU 上检查候选中线的自交，计算双向运动代价，并选择跨帧的中线及头尾顺序。骨架提取和 OpenCV 稀疏光流在 CPU 上执行。同一帧的各个候选共享一次批量光流跟踪。每条虫的 `run.json` 保存序列评分设备及设备名称。

同一次求解重试其他标记或缩短片段时复用已经测得的光流。标注帧和视频指标共用原始掩膜上的横截面测量。从中线沿两侧法向查找首个亚像素轮廓交点，按弧长积分计算平均体宽和圆台体积。头尾外观算法仍使用自己的距离变换特征。视频编码共享 `video_encoding.py`，支持 NVENC 与软件 H.264，输出前按实际尺寸探测硬件。SAM2 优先将能容纳的时序状态和输入帧放入显存，并为推理激活保留空间。

`body_sequence_solver.signature()` 覆盖图像外观、头端标注归一化、基础中线测量与输入缓存依赖，包括拆出的共享几何、头尾证据、图像、跟踪记录和序列化模块。更新代码后，旧结果保留供查看；继续计算时按签名检查决定重算，不绕过已有的输出内容校验。

大批逐帧 JSON 记录逐条序列化到临时文件，全部成功后再替换目标，避免同时构造整段记录副本和完整 JSON 字符串。视频导出校验一次建立帧与虫体索引，并且每条压缩中线只解压一次。文件树在单次渲染中建立索引，下一次渲染重新读取状态；后台后代查询按父子关系遍历，取排序编号不再排序整个列表。

结果视频选择由 `run_storage.py` 管理，进度模块无需导入会话控制器。掩膜修正由调用方传入标注会话构造函数，避免修正模块反向导入界面入口。任务配置与线程快照仍保留需要的独立副本；输入校验、事务回滚、可选预览隔离和旧结果读取兼容各自保持在对应边界。

复核派生任务通过 `run_storage.copy_tracking_snapshot()` 共享 `sam2-tracking/masks/` 下的 PNG 数据块，其它文件独立复制。所有程序内掩膜改写都通过 `write_png()` 调用 `replace_bytes()` 替换已有文件，使写入只影响当前任务；新的输出文件走普通写入路径。不支持硬链接时退回完整复制。后续新增掩膜写入入口也必须使用该替换函数，不能原地修改共享文件；对原始 PNG 的外部手工编辑不受程序的写入隔离保护。

历史中线方法的实现已移除，旧结果只能以只读方式查看；`centerline_methods.py` 保留其名称映射用来定位历史结果目录。纯源码导出排除历史模型缓存、视频和开发报告。桌面构建从单独的素材目录打包表征识别与通道计数两段示例，工作台按项目打开对应原片。

Electron 主进程启动本地 Python 服务，并在 Chromium 窗口中载入工作台。页面使用原生 JavaScript 和 Canvas，渲染进程启用沙箱并关闭 Node 集成。Node 运行时随 Electron 一起分发。GPU 模型按任务加载。

本地 HTTP 服务并发接收连接，工作区命令通过同一把锁顺序更新状态。传输文件内容期间，其他请求仍可进入；上传完成后重新检查目标文件夹或当前视频会话。标注页通过 `POST /api/prediction` 提交预测，用标注令牌和返回的任务 ID 查询结果。每次只执行一个预测，切换标注帧或模式会使旧结果失效。原有 `POST /predict` 仍直接返回预测结果。

工作台在请求入口校验本机地址与实际监听端口。帧预览使用独立加锁的单视频解码器，静态文件、抽帧和已保存时间线的读取可与进度轮询并行。进度页与工作台携带上一份进度的版本；阶段、队列和导出状态相同时仅返回计时。预览按序保留，以支持暂停和修正当前帧；切换到下一次计算或关闭会话时清理本会话生成的旧预览。历史结果索引在一次目录扫描中批量更新。

在线发行包在 Python 启动前由 `tools/electron/online-setup.cjs` 准备运行组件。`component-download.cjs` 负责 HTTP 续传、长度与哈希校验；本地准备页面通过受限 IPC 交换状态与操作。硬件检测、归档解压和原生运算验证位于 `src/platforms/online.cjs`。清单由 `tools/release/build_online.py` 在构建时生成并内置于首包。模型和环境分别按内容标识保存在用户目录，只有通过验证的临时环境才会启用，软件更新复用兼容组件，旧环境与实验结果继续保留。

Windows GPU 组件使用锁文件固定的官方 wheel，按上海交大镜像、阿里镜像、官方源的顺序下载。仅连接、响应或内容校验失败触发切源；用户暂停和本地文件错误直接返回。各来源共享以 SHA-256 命名的断点文件，完整校验后，由临时环境中的便携 Python 调用 `windows_gpu.py` 解压运行文件。镜像地址变化不改变组件身份；基础环境、CPU 和模型仍可复用已发布的归档。

布局由 `web/workspace-links.js` 管理，主工作台与标注/进度 iframe 共用一个存储实例。`GET/POST /api/layout` 使用当前会话令牌校验写入，校验有限数值和组件键，原子合并到 `config/layout.local.json`。浏览器缓存只作为启动暂存，服务端已有记录优先，布局不依赖临时端口。窄视口把面板放进可切换的工具区，保留桌面几何。布局重置不触碰标注与分析数据。

文件树由 `web/library-tree.js` 呈现，`POST /api/library-tree` 校验会话后执行工作区操作。`workspace_library.py` 的 v2 索引记录 folders、parent、order、collapsed，以及文件 removed 标记；旧 relativePath 索引自动迁移。所有树操作只改变引用，历史目录扫描使用 auto 注册，避免恢复已移除条目。从文件树移除正在使用的视频或其上级文件夹时，当前任务继续通过原路径读写，可通过“返回当前分析”继续。

Windows 桌面版的软件更新通过 `src/platforms/app_update.cjs` 与 `app_update.ps1` 执行。只有带 SHA-256 的 ZIP 更新包可使用“重启并更新”；用户确认退出后，程序在安装目录同级的隐藏更新目录内准备文件，检查包路径和版本。主窗口通过未保存修改检查后启动独立助手，助手等待应用进程退出后交换程序目录，最近一次旧版备份保存在隐藏更新目录内；交换或启动进程失败时恢复旧目录。该机制不代表新版业务启动健康检查，实验数据和组件缓存始终位于用户目录。源码运行及其他平台继续使用手动安装入口。

在线版首次准备默认选择 CPU；设置页显式开启 GPU 准备时复用同一 `Setup` 和下载窗口，不替换当前进程的环境。GPU 验证及原子启用成功后记录选择，下次启动使用 GPU。既有兼容 GPU 环境通过相同 ready 标识检查后继续复用；CPU 偏好优先于自动复用。
